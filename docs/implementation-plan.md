## 按优先级执行

1. **P0：准备可重复执行的部署脚本。** 保全服务器独有提交 fb6fc8f，不直接 reset 或在分叉上 pull。脚本、systemd/Nginx 模板纳入仓库。接收明确的提交 SHA，在独立 release 目录准备代码、按锁文件安装依赖和构建，失败时保持现行版本。固定 Node 22.22.1、uv 0.12.3，Python 暂保留线上 3.14；使用明确的工具路径。生产依赖用 uv 锁定同步并排除开发依赖。个人网站与 /trip 的部署目录、服务保持独立。
2. **P0：接通 GitHub 到服务器的部署权限。** 配置专用部署 SSH 密钥、服务器地址/用户名和预先核对的主机公钥；不复用个人管理员私钥。部署账号仅能写个人网站发布目录并执行必要的服务重启。现有 ubuntu 可无密码执行全部 sudo，不适合作为直接交给 CI 的默认权限。GitHub 凭据是否已有、云安全组是否允许 Actions 访问尚未核实，不能把本机 SSH 成功当作 CI 连通成功。
3. **P0：接入自动触发。** 在现有 CI 中增加依赖全部 check 成功的 deploy 作业，仅 push 到 main 时执行；部署此次已验证的 SHA，不重新取一个可能变化的 main HEAD。发布作业串行执行，不中途取消正在切换的发布；服务器端加锁并拒绝旧提交覆盖新版本。PR 和其他分支仅检查，不取得部署凭据。
4. **P0：验证和回退。** 保留上一 release；准备成功后切换 current 指向并重启个人网站服务。检查服务 active、/api/health、首页及其静态资源，记录实际发布 SHA；失败则切回上一 release、重启并再次检查。首次接入需单独授权维护窗口，调整 Nginx/systemd 路径；短暂重启中断可接受与否待用户确认，不承诺零停机。不要改动旅行助手路由或服务。
5. **P1：首次验收后启用日常使用。** 先验证正常发布与失败回退，再用小改动验证一次“合并 → CI → 部署 → 页面更新”。配置 main 必须通过 CI 才可合并，确认 GitHub 部署失败通知。保留少量历史 release，后续再按实际需求增加运维功能。

建议顺序：先本地编写脚本和工作流草稿并检查，再另行授权服务器初始化和首次部署，最后启用 main 自动部署。避免把已启用的部署工作流先合并而意外上线。

验收标准：CI 失败不会部署；成功发布准确的 SHA；失败可恢复上一版本；/trip 不受影响；日常合并无需手动 SSH。

未核实：GitHub Secrets/Environment、仓库 Webhook、云安全组与 Actions 到服务器的实际连通、分支保护；本次服务器常见定时器/cron/服务名检查未发现自动发布入口，但不据此排除全部外部自动化。

清理条件：自动部署实施并验收后，将使用和回退说明迁入 README，证据留在验证记录，清理本计划的历史状态。
